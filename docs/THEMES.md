# نظام الثيمات (متجر الثيمات)

هذا الملف يشرح كيف يعمل نظام الثيمات في سبعة، وكيف يُضاف ثيم جديد للمنصة.

## الفكرة الأساسية

الثيم في سبعة **كود**، وليس بيانات فقط. كل ثيم هو مجموعة مكوّنات React مستقلة
تُعيد رسم نفس الأقسام (hero, property_grid, about/why_us, contact) بشكل
مختلف بصريًا. البيانات نفسها (العنوان، الوصف، الصور، الألوان، الخط) محايدة
تمامًا تجاه الثيم — تُكتب مرة واحدة في محرر الموقع بالداشبورد، وأي ثيم
يعرضها بطريقته الخاصة.

هذا يعني: تبديل الثيم لا يغيّر أي بيانات مخزّنة، فقط طريقة عرضها.

## أين يعيش كل جزء

| الطبقة | المكان | المسؤولية |
|---|---|---|
| قاعدة البيانات | جدول `themes` (migration 0023) | اسم الثيم، `key` (مرجع برمجي ثابت)، `order_index`، `is_active` |
| سجل الثيمات | `apps/public-site/src/components/themes/registry.ts` | يربط كل `key` بمجموعة مكوّناته |
| مكوّنات كل ثيم | `apps/public-site/src/components/themes/<key>/` | التنفيذ البصري الفعلي |
| اختيار الثيم | `apps/dashboard` — صفحة `/site`، "متجر الثيمات" | العميل يختار من الثيمات النشطة (`is_active = true`) |
| إدارة الميتاداتا | `apps/console` — صفحة `/themes` | صاحب المنصة يعدّل الاسم/الترتيب/التفعيل فقط |

`api` يحسم `theme_id → theme_key` في `GET /v1/public/website` قبل أن يصل
الرد لـ `public-site` — public-site لا يستعلم قاعدة البيانات عن الثيمات
إطلاقًا، فقط يستقبل `theme_key` جاهزًا ويبحث عنه في السجل محليًا.

## كيف تُضيف ثيمًا جديدًا (للمطوّرين)

1. **صمّم الشكل** — كيف يبدو كل قسم (hero, property_grid, about/why_us,
   contact) في هذا الثيم. لا حاجة لتصميم قسم `footer`: شارة سبعة السفلية
   ثابتة في كل الثيمات ولا تُخصَّص.

2. **ابنِ مجموعة المكوّنات** في مجلد جديد، مثال `modern`:
   ```
   apps/public-site/src/components/themes/<key>/
     hero-section.tsx
     property-grid-section.tsx
     text-section.tsx
     contact-section.tsx
     index.ts   ← يصدّر { HeroSection, PropertyGridSection, TextSection, ContactSection }
   ```
   كل مكوّن يستقبل نفس الـ props بالضبط المعرّفة في
   `apps/public-site/src/components/themes/types.ts` (لا تُغيّر هذه الأنواع
   لثيم واحد — هي العقد المشترك بين كل الثيمات). يمكنك الاستعانة بثيم
   `classic` كمرجع، ويمكنك أيضًا بناء مكوّنات فرعية خاصة بالثيم (مثل
   `modern/modern-property-card.tsx`) إن أردت بطاقة عقار مختلفة الشكل —
   المهم أن الأربعة مكوّنات المُصدَّرة من `index.ts` تطابق التوقيع المطلوب.

3. **سجّله** في `apps/public-site/src/components/themes/registry.ts`:
   ```ts
   import { myNewTheme } from './my-new-key';
   const THEME_REGISTRY: Record<string, ThemeSectionComponents> = {
     classic: classicTheme,
     modern: modernTheme,
     'my-new-key': myNewTheme, // أضف هذا السطر فقط
   };
   ```

4. **أضف صفًا في قاعدة البيانات** عبر migration جديدة (راجع
   `supabase/migrations/0023_themes_registry.sql` كمثال):
   ```sql
   insert into themes (name_ar, name_en, key, order_index, is_active)
   values ('اسم الثيم', 'Theme Name', 'my-new-key', 2, true);
   ```
   `key` هنا يجب أن يطابق حرفيًا المفتاح المستخدم في السجل بالخطوة 3.

5. **اختبر التجاوب إلزاميًا** على ثلاث نقاط توقف على الأقل قبل الدمج:
   جوال (~390px)، تابلت (~768px)، كمبيوتر (~1280px). أي ثيم لا يعمل بشكل
   سليم على الثلاثة لا يُشحن — هذا شرط ثابت لكل ثيم في هذا النظام، وليس
   اختياريًا.

6. **بعد الدمج**، الثيم يظهر تلقائيًا في "متجر الثيمات" بالداشبورد (إن كان
   `is_active = true`)، وفي صفحة "الثيمات" بالكونسول لإدارة اسمه/ترتيبه/تفعيله.

## ما لا يمكن فعله من الكونسول (بالتصميم)

الكونسول **لا** يملك نموذج "إنشاء ثيم جديد". `key` ومجموعة المكوّنات
البرمجية لا يمكن تعديلهما من أي واجهة — تعديلهما من الكونسول يعني كسر
موقع كل عميل يستخدم ذلك الثيم فورًا. إنشاء ثيم هو دائمًا عمل برمجي (الخطوات
أعلاه)، وليس عملية تُدار ذاتيًا (no-code) من صاحب المنصة.
